# SQL Server Capture

Use [scripts/sql_capture.py](scripts/sql_capture.py) when documentation, API responses, and direct queries do not explain the SQL produced by a real workflow. Reuse evidence already gathered.

## Setup

Initialize the launcher in the PowerShell process that runs the commands; shell functions do not persist between separate tool calls:

Resolve `$sqlCaptureRoot` to the directory containing this `SKILL.md` from the skill catalog. The sibling API skill is bundled in the same plugin:

```powershell
$sqlCapture = Join-Path $sqlCaptureRoot 'scripts\Invoke-SqlCapture.ps1'
$runApi = Join-Path (Split-Path -Parent $sqlCaptureRoot) 'run-api-requests\scripts\Invoke-RunApi.ps1'
```

Both launchers use the plugin's pinned `requirements.lock`. Keep the complete plugin layout.

Requirements: Python 3.11+, `uv`, a SQL Server ODBC driver, and permission to manage Extended Events sessions and read their event files. Use the sibling `$run-api-requests` and `$sql-server` skills for API commands and direct queries.

## Target and execution

| Profile | SQL Server | Default database |
| --- | --- | --- |
| `local` (default) | Machine profile | Machine profile |
| `internal` | Machine profile | Machine profile |

Use `local` unless the user requests internal. Preserve an explicit database with `--database`. Capture options select only the SQL connection, so configure the wrapped command for the same target.

Run the authorized workflow once within the relevant capture window. Capture does not roll back the wrapped command. If a write's outcome is ambiguous, inspect the API result and database state before retrying; stop when that outcome cannot be resolved safely.

```powershell
& $sqlCapture around --server local --database <database> -- pwsh -NoProfile -File $runApi erp get shipment 000014
```

Replace example identifiers with task values. Put capture options before `--`; everything after it must be an executable and its arguments, not PowerShell syntax or a shell function.

| Option | Effect |
| --- | --- |
| `--client-app PX.Data.PXGraph` | Case-insensitive client application substring |
| `--contains-text SOShipment` | Case-insensitive SQL text substring |
| `--event-name sql_statement_completed` | Event name; repeat to include multiple types |
| `--post-wait-seconds 2` | Wait after the command; default is two seconds |

The session collects completed RPCs, batches, and statements. Filtering occurs when reading the event file. Returned events match the time window and database and exclude helper/session SQL and `sp_reset_connection` noise. App and text filters narrow evidence but do not uniquely identify a request on a busy server.

For a local shipment creation with before/after table comparisons, read [shipment diffs](references/shipment-diff.md). That mode is intentionally localhost-only and lacks company filtering. Use `around` with an explicitly targeted command and company-scoped queries for internal or multi-company work.

## Interpret the result

The helper emits one JSON object. Inspect `ok`, `error`, and `command_result` (`exit_code`, `stdout`, `stderr`, and parsed `stdout_json` when available). A zero process exit does not establish the business outcome; inspect the API payload and identifiers.

`capture_meta` records the profile, database, UTC window, event session/file path, driver, and filters. Compare `raw_event_count` with `filtered_event_count` to assess discarded activity. Each event has `event_name`, `utc_timestamp`, `client_app_name`, `database_name`, `text`, `duration_ms`, `cpu_ms`, and `row_count`.

Report the target, command outcome, counts, and SQL or row changes that answer the question. Separate observation from inference. Zero filtered events do not prove that no SQL ran; check target alignment, filters, and timing. Do not repeat a mutating action merely to improve the trace.

The helper attempts to drop its temporary session and removes local event files even when capture fails. Event files on a remote SQL host may remain. The recorded path is diagnostic metadata, not a retained artifact.

## Authentication

Local uses Windows integrated authentication. Internal reads Windows Credential Manager target `Codex.SqlServer.internal` through [scripts/credential_manager.py](scripts/credential_manager.py).

A complete process-environment pair overrides either profile: `VISMA_SQL_LOCAL_USER` / `VISMA_SQL_LOCAL_PASSWORD`, or `VISMA_SQL_INTERNAL_USER` / `VISMA_SQL_INTERNAL_PASSWORD`. An incomplete pair fails rather than mixing sources. Keep credentials out of skill files, command arguments, source control, and output; redact sensitive SQL literals when reporting captures.

## Machine configuration

Profiles are loaded from `%LOCALAPPDATA%\Visma\Codex\erp-dev-tools\profiles.json`, or `ERP_DEV_TOOLS_CONFIG` when explicitly set. Override endpoints with `VISMA_SQL_LOCAL_SERVER` / `VISMA_SQL_LOCAL_DATABASE` or `VISMA_SQL_INTERNAL_SERVER` / `VISMA_SQL_INTERNAL_DATABASE`. An explicit database argument wins. Keep credentials in the protected stores described above.
